# 4.3 Training Pipeline

This section describes the machine learning training pipeline implemented within the IKMS backend. As designed in Chapter Three, Section 3.8, the pipeline is a sequential, multi-stage process that automatically transforms the raw text of an uploaded research document into structured, analyzable data. The pipeline is triggered every time a new document is submitted to the system.

## 4.3.1 Dataset Size

The training corpus consisted of **2,500 research documents** sourced from the CORD-19 dataset and arXiv preprint repository, as described in Section 4.2. The total size of the raw PDF files in the training corpus was approximately **4.7 GB**. After text extraction, the resulting plain-text corpus amounted to approximately **580 MB** of raw string data, representing roughly **12 million tokens** prior to preprocessing.

For the TF-IDF vectorizer model, the vocabulary was capped at a maximum of **10,000 features** (unique terms), which was determined through experimentation to provide a good balance between representational richness and computational efficiency. Terms appearing in fewer than 5 documents (min_df=5) or more than 95% of all documents (max_df=0.95) were excluded, as they represent either too-rare noise terms or too-common text that adds little discriminative value.

| Parameter | Value |
|---|---|
| Total documents | 2,500 |
| Total tokens (pre-cleaning) | ~12,000,000 |
| Unique vocabulary (post-cleaning) | ~42,000 |
| TF-IDF max features | 10,000 |
| LDA number of topics | 10 |

*Table 4.3: Dataset and Model Parameters*

## 4.3.2 Dataset Training/Testing Split

To evaluate the performance of the machine learning models prior to integration, the 2,500-document corpus was divided into two subsets:

- **Training Set: 2,000 documents (80%)** — Used for fitting the TF-IDF vectorizer and training the LDA model.
- **Test Set: 500 documents (20%)** — Held out and used exclusively for evaluating model performance on unseen data.

The split was performed using a stratified random sampling approach to ensure that documents from each identified topic area were proportionally represented in both the training and test sets. This prevents the models from being inadvertently biased toward more frequently occurring topics during training.

| Split | Documents | Percentage |
|---|---|---|
| Training | 2,000 | 80% |
| Testing | 500 | 20% |
| **Total** | **2,500** | **100%** |

*Table 4.4: Training and Testing Split*

## 4.3.3 Description of the Training Process

The end-to-end training process for the IKMS machine learning pipeline was executed as follows:

### Step 1: PDF Text Extraction

Each PDF document in the training corpus was processed using the **PyMuPDF (fitz)** Python library. The library opened each file and iterated through its pages, extracting all selectable text blocks. The extracted text from all pages of a single document was concatenated into a single string. Documents that produced fewer than 100 words after extraction were discarded from the corpus, as they were likely scanned or image-only PDFs.

```python
import fitz  # PyMuPDF
def extract_text_from_pdf(file_path):
    doc = fitz.open(file_path)
    full_text = ""
    for page in doc:
        full_text += page.get_text()
    return full_text
```

### Step 2: Text Preprocessing and Cleaning

The extracted raw text was cleaned using the **NLTK** Python library through the following sequential steps:

1. **Lowercasing:** All characters were converted to lowercase to ensure uniformity (e.g., "Malaria" and "malaria" are treated identically).
2. **Punctuation and Special Character Removal:** All non-alphabetic characters, including punctuation, numbers, and special symbols (e.g., `%`, `©`, `+`), were removed using regular expressions.
3. **Tokenization:** The cleaned text was split into individual word tokens using NLTK's `word_tokenize` function.
4. **Stopword Removal:** A standard English stopword list from NLTK's corpus was applied, removing 179 common, low-information words (e.g., "the", "is", "a", "in"). The stopword list was also extended with domain-specific terms that were too common to be informative across health research documents (e.g., "study," "paper," "research," "result").
5. **Lemmatization:** Tokens were reduced to their linguistic base form using NLTK's `WordNetLemmatizer` (e.g., "patients" → "patient", "findings" → "finding"). This reduces vocabulary size and improves model generalization.

### Step 3: TF-IDF Vectorization and Keyword Extraction

The preprocessed text from all training documents was fed into **scikit-learn's `TfidfVectorizer`** to build a TF-IDF model. The fitted vectorizer transforms any document's text into a numerical vector, where each dimension corresponds to a term in the vocabulary and its value represents the term's TF-IDF score.

For each document, the top **15 terms** with the highest TF-IDF scores were extracted and stored in the database as the document's automated keyword tags. These keywords serve three purposes: they populate the document's metadata for search; they are displayed on the document detail page; and they form the basis of the cosine similarity calculation for the recommendation engine.

### Step 4: Topic Modeling with Latent Dirichlet Allocation (LDA)

The LDA model was trained using **scikit-learn's `LatentDirichletAllocation`** class on the TF-IDF matrix generated in Step 3. The model was configured to identify **10 latent topics** across the corpus, a number determined through experimentation using the topic coherence metric (see Section 4.4).

The training used the **online variational Bayes algorithm** (`learning_method='online'`), which processes the data in mini-batches, making it more memory-efficient for larger corpora. The model was trained for a maximum of **30 iterations** (`max_iter=30`), at which point coherence scores had stabilized.

After training, each document in the corpus was assigned a topic distribution (a probability vector across all 10 topics). The topic with the highest probability was assigned as the document's **primary topic**, which is stored in the `TopicScore` table of the database and displayed as the document's category tag within the IKMS interface.

### Step 5: Content-Based Recommendation (Cosine Similarity)

The recommendation engine is implemented at query-time rather than during the training phase. When a user views a specific document, the system retrieves its stored TF-IDF vector and computes the **cosine similarity** between it and all other approved documents in the repository using **scikit-learn's `cosine_similarity`** function. The top 5 documents with the highest similarity scores (excluding the document itself) are returned as recommendations.

This approach ensures that recommendations are always current and include newly uploaded documents, without requiring periodic model retraining.
